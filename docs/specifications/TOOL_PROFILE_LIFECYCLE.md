## 1. Overview

Tool Profiles define provider-specific CLI behavior interpreted by the generic Conclave CLI Worker Engine (`engines/cli_worker`).

Because Tool Profiles govern how provider executables are discovered, invoked, and supervised, changes to Profile behavior are treated with the rigor of executable code releases.

This specification defines the **single, immutable lifecycle** governing all Tool Profile changes—whether authored by human operators, generated by AI models, or produced through human-AI collaboration.

```text
+---------------------------------------------------------------------------------------+
|                                    DRAFT PHASE                                        |
|                                                                                       |
|   +--------------------+      +--------------------+      +--------------------+      |
|   |    Draft Create    | ---> |  Local Validation  | ---> |    Local Tests     |      |
|   |  (Human or AI)     |      |  (Schema & Limits) |      | (Engine & Sandbox) |      |
|   +--------------------+      +--------------------+      +--------------------+      |
|             |                                                       |                 |
|             + <--- (Payload edits update candidate digest) <------- +                 |
+---------------------------------------------------------------------------------------+
                                           |
                                           v [Publish & Sign]
+---------------------------------------------------------------------------------------+
|                              IMMUTABLE RELEASE PHASE                                  |
|                                                                                       |
|   +--------------------+      +--------------------+      +--------------------+      |
|   |      Testing       | ---> |        Beta        | ---> |       Stable       |      |
|   | (Immutable Release)|      | (Channel pointer)  |      | (Evidence gated)   |      |
|   +--------------------+      +--------------------+      +--------------------+      |
|             |                           |                           |                 |
+---------------------------------------------------------------------------------------+
              |                           |                           |
              v                           v                           v
+---------------------------------------------------------------------------------------+
|                               TERMINAL & EXCEPTION STATES                             |
|                                                                                       |
|                    +--------------------+      +--------------------+                 |
|                    |      Retired       |      |      Revoked       |                 |
|                    | (Archival / EOL)   |      | (Emergency Block)  |                 |
|                    +--------------------+      +--------------------+                 |
+---------------------------------------------------------------------------------------+
```

## 2. Core Lifecycle Principles

1. **One Unified Lifecycle:** The lifecycle is identical for human-authored and AI-generated changes. AI proposals never bypass validation, testing, human review, or signing gates.
2. **Drafts are Mutable; Releases are Immutable:**
   - In the `draft` state, payload JSON, compatibility ranges, and candidate digests may be edited.
   - Upon publication (`draft` → `testing`), the payload is cryptographically signed and permanently frozen.
   - Once published, a Profile payload, version, digest, or compatibility claim **never** changes in place.
3. **Modification Requires a New Release Version:** Any modification to a published Profile creates a new sequential draft release version (e.g., `Stable v12` $\to$ Edit $\to$ `Draft v13`).
4. **Promotion Changes Pointers and Lifecycle Only:** Promoting a release (`Testing` $\to$ `Beta` $\to$ `Stable`) updates channel pointers and lifecycle metadata. It **never** alters the Profile payload or digest.
5. **Rollback Moves Channel Pointers:** A rollback **never** edits or overwrites a release. It moves the channel pointer backward to an earlier, known-good, immutable release (e.g., `Stable pointer: v18` $\to$ `v17`).
6. **Revocation Forbids Execution:** Revoking an immutable release immediately clears channel pointers, adds the payload digest to revocation indexes, and causes Workspaces to fail closed if no alternate release is available.

## 3. Lifecycle States

The lifecycle defines six mutually exclusive states stored in `tool_profile_releases.lifecycle_state`:

| State | Mutability | Signature Required | Eligible Channel Pointers | Workspace Admission | Description |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `draft` | **Mutable** | No | None | **Forbidden** (Profile Lab sandbox only) | Active candidate undergoing editing, schema validation, and local CLI sandbox testing. |
| `testing` | **Immutable** | **Yes** (Ed25519) | `testing` | Workspaces on `testing` channel | Published and signed release deployed to testing Workspaces for integration verification. |
| `beta` | **Immutable** | **Yes** (Ed25519) | `testing`, `beta` | Workspaces on `testing` or `beta` channels | Promoted release evaluated in broader operational environments. |
| `stable` | **Immutable** | **Yes** (Ed25519) | `testing`, `beta`, `stable` | All Workspaces | General production release. Requires a Cloud-validated acceptance contract bound to the payload digest. |
| `retired` | **Immutable** | Yes | None | Existing executions finish; no new deployments | Deprecated release. Cannot be targeted by active channel pointers. |
| `revoked` | **Immutable** | N/A | None | **Rejected immediately** | Critical defect or security hazard. Channel pointers cleared automatically; execution blocked. |

## 4. State Transitions & Invariants

State transitions are strictly validated by Cloud registry routes and enforced in the database via the `tool_profile_lifecycle_transition_valid` D1 trigger.

```text
                                  +--------+
                                  | draft  |
                                  +--------+
                                   /   |  \
                 +----------------+    |   +----------------+
                 |                     |                    |
                 v                     v                    v
           +-----------+          +---------+          +---------+
           |  testing  |          | retired |          | revoked |
           +-----------+          +---------+          +---------+
            /    |    \
           /     |     +---------------+
          v      v                     v
     +------+  +---------+        +---------+
     | beta |  | stable  |        | retired |
     +------+  +---------+        +---------+
      /   \         |
     /     \        +-------------+
    v       v                     v
+--------+ +---------+       +---------+
| stable | | retired |       | revoked |
+--------+ +---------+       +---------+
    |           |
    v           v
+---------+ +---------+
| retired | | revoked |
+---------+ +---------+
```

### Transition Matrix:

| From State | Allowed Target States | Trigger / Requirement | Forbidden Transitions |
| :--- | :--- | :--- | :--- |
| `draft` | `testing`, `retired`, `revoked` | Publication requires valid Ed25519 signature over canonical signing message. | `beta`, `stable` (cannot skip testing) |
| `testing` | `beta`, `stable`, `retired`, `revoked` | Promotion requires operator authorization. `stable` requires acceptance evidence. | `draft` (cannot un-publish) |
| `beta` | `stable`, `retired`, `revoked` | `stable` promotion requires a Cloud-validated acceptance contract. | `draft`, `testing` |
| `stable` | `retired`, `revoked` | Retiring requires active channel pointer to be moved first. Revocation requires reason. | `draft`, `testing`, `beta` |
| `retired` | `revoked` | Emergency revocation of previously retired release. | `draft`, `testing`, `beta`, `stable` |
| `revoked` | *(None — Terminal)* | Irreversible security boundary. | Any transition out of `revoked` |

## 5. Detailed Step-by-Step Lifecycle

### Step 1: Draft Creation
- **Action:** An operator or AI proposal initializes a new Draft for a given `profileDefinitionId`.
- **Version Assignment:** Automatically assigned `MAX(release_version) + 1` for the definition.
- **Initial State:** `lifecycle_state = 'draft'`, `published_at = NULL`, `signature = NULL`.
- **Database Trigger:** Fires `tool_profile_release_draft_audit` inserting an audit row with action `draft_created`.
- **Cloud Synchronization:** Profile Lab reads the Cloud release at the candidate's definition and version. It creates an absent Cloud draft with `POST /api/admin/tool-profiles/:profileDefinitionId/releases`, then saves later edits with `PUT /api/admin/tool-profiles/:profileDefinitionId/releases/:version/draft`. A published release is immutable; editing it starts the next version and creates that Cloud draft with `POST`.

### Step 2: Local Validation
- **Action:** Executed within Profile Lab prior to running local tests.
- **Checks:**
  1. Strict JSON schema conformance against `Tool Profile v1`.
  2. Bounded limits validation (`TOOL_PROFILE_LIMITS`): payload $\le 256\text{ KiB}$, argument count, regex placeholder restrictions, forbidden shell constructs.
  3. Rejection of unknown properties.
  4. Logical Worker identity match against definition (`definition.worker_type_id == profile.logicalWorkerTypeId`).
  5. Discovery candidates contain `definition.provider_tool_name`.

### Step 3: Local CLI Testing (Test Sandbox)
- **Action:** Profile Lab executes the draft Profile candidate directly against the locally installed provider CLI using the generic CLI Worker Engine (`engines/cli_worker`).
- **Isolation:** The draft executes strictly as a `LocalDraftProfileCandidate` within the Profile Lab test sandbox. It is never admitted to normal Workspace storage or Cloud inventory.
- **Matrix:**
  1. Discovery & executable verification.
  2. Semver version command & compatibility extraction.
  3. Passive authentication/readiness probe.
  4. Live prompt probe.
  5. Controlled execution & output parsing (JSONL events).
  6. Session creation & session resumption.
  7. Timeout, error mapping, and cancellation process cleanup.
- **Evidence Binding:** A passing run emits the capability-aware Cloud evidence contract bound to the candidate's canonical SHA-256 `payloadDigest`. Profile Lab submits it as local qualification before publication. Cloud validates the submitted contract against the stored draft and returns the qualification ID required by publication.
- **Digest Binding:** If a draft edit changes its canonical payload, its `payloadDigest` changes. A record for the prior digest cannot qualify the changed payload.

### Step 4: Publish & Freeze (`draft` $\to$ `testing`)
- **Action:** Profile Lab operator requests release publication.
- **Preconditions:**
  1. The complete local Test Ladder passes and a fresh qualification record is stored in Cloud for the current `payloadDigest`.
  2. Candidate payload passes static validation.
  3. User holds `profiles:release:manage` or `profiles:admin` authority.
- **Signing Ceremony:**
  1. Profile Lab submits the local sandbox contract to the draft qualification endpoint; Cloud checks identity, digest, supported Engine/provider versions, freshness, and all required scenario statuses before storing an immutable qualification record.
  2. Profile Lab submits the returned `qualificationEvidenceId` with the publish request. Cloud reloads and revalidates that record against the current draft, checks user authorization and signer readiness, then signs the canonical message:
     ```text
     CONCLAVE_TOOL_PROFILE_RELEASE:v1:<publisher>:<signingKeyId>:<payloadDigest>:<profileDefinitionId>:<releaseVersion>:<logicalWorkerTypeId>:<engineFamily>:<minEngine>:<maxExclusiveEngine>
     ```
  3. Cloud updates the release record: `signature`, `signing_key_id`, `publisher`, `published_at = NOW()`, `lifecycle_state = 'testing'`. The lifecycle audit records the qualification ID.
- **Database Trigger:** `tool_profile_release_payload_immutable` activates. From this timestamp forward, any SQL UPDATE targeting payload or identity fields will abort with:
  `"published Tool Profile release payload is immutable"`.
  Any DELETE will abort with:
  `"published Tool Profile releases cannot be deleted"`.

### Step 5: Promotion to Beta (`testing` $\to$ `beta`)
- **Action:** Release is promoted to the `beta` channel.
- **Payload Effect:** **ZERO.** Payload JSON, signature, and digest remain completely identical.
- **Database Operations:**
  1. Update `tool_profile_releases.lifecycle_state = 'beta'`.
  2. Update `tool_profile_channel_pointers` for channel `'beta'` to point to `release_version`.
  3. Audit row inserted: `promoted_to_beta`.

### Step 6: Promotion to Stable (`beta` or `testing` $\to$ `stable`)
- **Action:** Release is promoted to the production `stable` channel.
- **Evidence Gate:** Stable promotion requires an acceptance contract stored in `tool_profile_acceptance_evidence` and meeting the Cloud checks in the [Tool Profile Evidence-Bound Promotion Contract](TOOL_PROFILE_EVIDENCE_CONTRACT.md):
  - Must match the release's exact `payload_digest`.
  - Must be referenced by its stored `acceptanceEvidenceId`; promotion requests do not carry evidence JSON.
  - Cloud reloads the immutable record and revalidates all eight capability-aware scenarios.
  - The client-reported provider CLI version must be within the Profile's declared range. Cloud cannot attest to the local binary.
  - Must be no older than 90 days.
- **Payload Effect:** **ZERO.** Payload is never edited.
- **Database Operations:**
  1. Before promotion, submit evidence separately to Cloud; Cloud inserts the validated record into `tool_profile_acceptance_evidence` and returns its ID.
  2. Promotion references that stored evidence ID, which Cloud revalidates against the exact release digest.
  3. Update `tool_profile_releases.lifecycle_state = 'stable'`.
  4. Update `tool_profile_channel_pointers` for channel `'stable'` to point to `release_version`.
  5. Audit row inserted: `promoted_to_stable`, with the evidence ID recorded in its reason.

Cloud checks the submitted contract and stores it immutably, but does not
observe local Engine or provider execution. The Profile Lab flow emits a
contract only after its applicable local scenarios pass; Cloud API access alone
does not prove that the submitter used that flow. See the [evidence contract](TOOL_PROFILE_EVIDENCE_CONTRACT.md)
for the trust boundary and the separately tracked real-provider rollout gates.

## 6. Rollback Mechanics

A rollback **never modifies, overwrites, or deletes** a published Profile release.

When an operational defect is discovered in a release currently pointed to by an active channel:
1. An authorized operator initiates a rollback to an earlier release version $v_{\text{target}}$ where $v_{\text{target}} < v_{\text{current}}$.
2. Cloud validates that $v_{\text{target}}$:
   - exists for the definition;
   - is signed and published;
   - is in an eligible lifecycle state (`testing`, `beta`, or `stable`);
   - is not `retired` or `revoked`.
3. Cloud updates `tool_profile_channel_pointers`:
   ```sql
   UPDATE tool_profile_channel_pointers
      SET release_version = ?targetVersion,
          modified_by_user_id = ?actorUserId,
          updated_at = ?now
    WHERE profile_definition_id = ?definitionId AND channel = ?channel;
   ```
4. Audit row inserted with action `stable_rollback` (or `channel_promoted` if moving pointers) recording `previous_release_version` and target version.
5. Workspaces subscribed to the channel automatically synchronize to the earlier release on their next poll or reconnect cycle.

## 7. Retirement and Revocation (Terminal / Exception States)

### Retirement (`retired`)
- **Purpose:** Graceful end-of-life for an obsolete release.
- **Constraint:** A release cannot be retired while an active channel pointer still targets it. The operator must first roll back or advance the channel pointer.
- **Behavior:** Existing running assignments complete; no new Workspaces will be directed to this release version.

### Revocation (`revoked`)
- **Purpose:** Emergency termination of an untrusted, unsafe, or critically defective Profile release.
- **Triggers:**
  - Security vulnerability or command injection risk;
  - Unsafe provider CLI arguments or permission bypass;
  - Critical output parsing failure causing data corruption;
  - Provider account compromise or compromised signing key.
- **Procedure:**
  1. Operator invokes revocation with mandatory justification `reason` ($\le 512$ chars).
  2. Cloud sets `lifecycle_state = 'revoked'`, `revoked_at = NOW()`.
  3. Database trigger `tool_profile_release_clear_revoked_channels` fires automatically:
     ```sql
     DELETE FROM tool_profile_channel_pointers
      WHERE profile_definition_id = NEW.profile_definition_id
        AND release_version = NEW.release_version;
     ```
  4. Workspaces receiving the updated catalog or revocation notice immediately purge the revoked release from their local cache (`tool_profiles/`) and refuse to launch processes with it.

## 8. Human vs. AI Provenance and Parity

Conclave maintains strict architectural parity between human operators and AI agents:

```text
                  +---------------------------+
                  |   Draft Profile Change    |
                  +---------------------------+
                                |
                 +--------------+--------------+
                 |                             |
                 v                             v
       [ Human-Authored ]              [ AI-Generated ]
                 |                             |
                 +--------------+--------------+
                                |
                                v
               Identical Candidate Validation
                                v
               Identical Local Engine Sandbox Tests
                                v
               Identical Digest-Bound Evidence
                                v
               Human Review & Publish Request
                                v
               Cloud / CI Cryptographic Signing
                                v
               Immutable Profile Release
```

### Invariants:
1. **Identical Lifecycle Contract:** AI-generated Profile modifications follow the exact same state machine as human modifications. There is no "fast path", "AI bypass", or unsigned execution path.
2. **AI Changes Always Create Drafts:** An AI tool may generate a candidate payload or patch, but it can only write to a `draft` release record. It cannot directly publish, promote, or sign.
3. **Mandatory Human Confirmation for Production:** Promoting to `stable` or executing a production `revocation` requires explicit human operator confirmation.
4. **Provenance Metadata:** When a Draft is created or updated by an AI model, the audit record captures:
   - author type (`human`, `ai_generated`, `ai_assisted`);
   - model identifier and prompt hash;
   - source release digest from which the draft was derived;
   - human reviewer ID who inspected the diff.

## 9. Verification & Invariant Checklist

Every component interacting with Tool Profiles must enforce these invariants:

- [x] **No In-Place Edits:** `tool_profile_releases` rows with `published_at IS NOT NULL` reject all updates to payload, compatibility, version, or digest.
- [x] **Strict Forward Versioning:** Draft releases must use strictly incrementing integer versions.
- [x] **Signed Payloads Only in Workspaces:** Workspaces admit only releases with valid Ed25519 signatures verified against trusted publisher public keys.
- [x] **Unsigned Drafts Confined to Sandbox:** Unsigned drafts execute only in Profile Lab's local test sandbox.
- [x] **Rollback by Pointer:** Rollback moves channel pointers to earlier valid versions without mutating any release row.
- [x] **Automatic Revocation Pointer Clearing:** Revoking a release instantly removes it from all active channel pointer tables.
- [x] **No Provider Credentials:** Provider secrets never enter Profile JSON, release payloads, test evidence, or audit tables.
